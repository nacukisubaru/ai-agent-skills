# Feature workflow

Единый процесс для любой задачи, которую нельзя сделать одним шагом.

## When to use

- Пользователь приложил ТЗ, макет, спецификацию.
- Задача требует больше ~3 шагов или затрагивает несколько слоёв.
- Нужно продолжить ранее начатую задачу.

## 1. Папка задачи

Создать в корне репозитория:

```
.github/tasks/<slug>/
├── plan.md          # фазы и критерии готовности
├── decisions.md     # принятые решения и открытые вопросы
├── progress.md      # журнал: что сделано, что сломано, что дальше
├── review-1.md      # отчёты ревью по фазам
├── test-1.md        # результаты прогонов
└── source/          # ТЗ и приложения, как их дал пользователь
```

Правила:

- `<slug>` — короткий kebab-case (`notifications`, `lot-import-v2`).
- ТЗ копируется **как есть** в `source/`, без переименования содержимого. Имя файла — латиницей.
- Если папка уже есть — дополнять, не пересоздавать.
- Документация фичи для людей и агентов пишется в `.github/docs/`, а не сюда. Здесь только рабочие артефакты задачи.

## 2. plan.md

Обязательные разделы:

```markdown
# <Название> — план

## Источники
- ссылки на файлы в source/

## Решения
- краткие ссылки на decisions.md

## Разведка: что есть / чего нет
| Блок | Состояние | Где смотреть |

## Фазы
### Фаза N. <Название>
- задачи списком;
- затрагиваемые файлы и миграции;
- **Definition of Done**: проверяемое утверждение, а не «работает».

## Риски
## Открытые вопросы
```

Требования к фазам:

- Фаза заканчивается **видимым результатом**: запись в БД, страница, письмо, зелёный тест.
- Предпочитать вертикальные срезы (событие → БД → UI), а не слои (сначала весь бэк, потом весь фронт).
- Большая фаза делится на подфазы (`3a`, `3b`), каждая проверяется отдельно.
- В плане сразу указано, что делать с существующими миграциями: только добавочные.

Правила ведения:

- После каждой фазы обновлять статус в таблице фаз (`[ ]` → `[~]` → `[x]`).
- Изменение плана фиксировать в `progress.md`, а не молча.

## 3. Цикл фазы (обязательный порядок)

Фаза выполняется **итерациями**, а не одним проходом. Одна итерация:

```
1. Реализация порции работы
2. Линт/синтаксис + автотесты
3. Ручная проверка результата (браузер, curl, прогон сценария)
4. code-review            → отчёт в review-N.md
5. Правки по находкам
6. Повторная проверка пунктов 2–3
```

После шага 6 обязательно решается: **есть ли ещё находки**.

- Если в ревью или на проверке нашлась проблема уровня critical/high —
  **следующая итерация обязательна**. Она начинается с шага 1, а не с коммита.
- Если остались только low/косметика — их можно закрыть в этой же итерации
  или осознанно отложить, записав в `progress.md`.
- Коммит делается только после итерации, в которой **не осталось
  незакрытых critical/high**. Иначе сначала итерация, потом коммит.
- Количество итераций не ограничено. «Сделал один раз и отдал» запрещено,
  если проверка показала расхождение с макетом, ТЗ или поведением.
- Итерация, которая ничего не изменила и не добавила проверок, не считается:
  она должна либо закрывать находку, либо добавлять доказательство (тест,
  скриншот, лог).

Каждая итерация фиксируется в `review-N.md` (или `test-N.md`) коротко:
что проверялось, что нашли, что исправили, что осталось.

Запрещено:

- Пропускать ревью, потому что «тесты прошли». Тесты и ревью — разные проверки.
- Переходить к следующей фазе, пока предыдущая не зелёная.
- Коммитить при незакрытых critical/high.
- Считать фазу готовой, если визуальная часть не сверена с макетом на
  десктопе и на мобильной ширине.

## 3.1. Обязательная визуальная сверка

Если задача про вёрстку или UI:

1. Открыть результат в браузере на **десктопной** ширине (≥1280) и на
   **мобильной** (≈390). Скриншот обеих.
2. Сравнить с макетом: порядок блоков, отступы, шрифты, цвета, состояния
   (пусто / загрузка / ошибка / успех).
3. Отдельно проверить, что страница не «съёживается» в узкую колонку на
   большом экране и не ломается на узком.
4. Найденное расхождение — находка, а не «на усмотрение»: либо исправить,
   либо записать причину в `progress.md`.

## 4. Definition of Done фазы

Фаза считается готовой, когда одновременно:

- все пункты фазы из `plan.md` выполнены;
- unit-тесты на новую логику есть и зелёные;
- сценарий ручной проверки написан и прогнан (если менялся бэк);
- UI проверен в браузере (если менялся фронт);
- ревью проведено, находки critical/high исправлены;
- отчёты записаны в папку задачи;
- коммиты сделаны.

## 5. Шаблон progress.md

```markdown
# Прогресс

## <дата> — Фаза N
- Сделано:
- Проверено:
- Найденные проблемы и как исправлены:
- Открытые вопросы:
- Коммиты:
```

## 6. Открытые вопросы

Если для продолжения нужно решение пользователя — зафиксировать вопрос в `decisions.md` и задать его через инструмент вопроса. Не выбирать молча вариант, который меняет поведение системы.

# Manual testing

Unit-тестов недостаточно, когда логика зависит от БД, очередей, Bitrix-событий и настроек пользователя.

## When to use

- Изменения в сервисах, обработчиках, очередях, миграциях.
- Нужно доказать, что данные реально пишутся и не дублируются.
- Перед коммитом фазы.

## Доступы

Для сценариев, которым нужен пользователь (личный кабинет, права, уведомления),
доступы берутся из `.github/PROJECT-ACCESS.md` (имена переменных) и
`.github/.env.local` (значения): `RAD_BASE_URL`, `RAD_ADMIN_LOGIN` / `RAD_ADMIN_EMAIL`,
`RAD_ADMIN_PASSWORD`. Нужного пользователя там нет — **спросить у пользователя**,
не подбирать и не заводить нового. В сценарий и вывод прогона пароль не печатать.

## Где лежит

```
project/.github/tests/<slug>/
├── scenario.md   # сценарий
└── run.php       # прогон (или несколько скриптов)
```

Одна задача — одна папка. Скрипт запускается из `project/`:

```bash
docker compose run --rm --no-deps php-cli php .github/tests/<slug>/run.php
```

## 1. Сначала сценарий, потом код прогона

`scenario.md` содержит:

- группу проверок;
- ID каждой проверки (`T01`, `P01`, ...);
- проверяемое утверждение;
- ожидаемый результат.

Проверки идут **от общего к частному**:

1. Базовый сценарий работает.
2. Ветвления по настройкам и правам.
3. Пустые и отсутствующие данные.
4. Дубли и повторный запуск.
5. Конкурентность и блокировки.
6. Лимиты и пороги.
7. Ошибки внешних систем.
8. Изоляция между пользователями.
9. Очистка после прогона.

## 2. Скрипт

Требования:

- Создаёт свои данные с уникальными идентификаторами.
- Не полагается на существующих пользователей и лоты.
- Каждая проверка печатает `OK`/`FAIL` с ID.
- В конце — итог `N OK, M FAIL` и код возврата `1` при провале.
- В `finally` удаляет всё созданное, даже при падении.
- Секреты и пароли не печатает.

Скелет:

```php
check('T01 событие создано', is_int($eventId) && $eventId > 0);
```

## 3. Прогон и фиксация

- Запустить скрипт, добиться `0 FAIL`.
- Краткий результат дописать в `scenario.md` (блок «Результат прогона»).
- Отчёт по фазе — `.github/tasks/<slug>/test-N.md`.

## 4. Запрещено

- Оставлять тестовые записи в БД.
- Проверять «на глаз» без записанного сценария.
- Считать прогон успешным, если были `FAIL`, даже «незначительные».
- Коммитить временные страницы, скрипты входа и дампы.

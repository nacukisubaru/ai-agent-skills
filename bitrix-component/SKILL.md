# Bitrix component

Если задача про вёрстку по готовому макету (Figma, HTML, скриншоты), сначала
загрузи `layout-from-mockup`: он задаёт границы поверхности, запрет старых
стилей и parity-тест. Этот скилл — про реализацию компонентов и ассетов.

## Структура компонента

```
local/components/<vendor>/<name>/
├── class.php            # один класс-наследник CBitrixComponent
├── .description.php     # имя и раздел для дерева компонентов
├── .parameters.php      # параметры (если компонент переиспользуемый)
└── templates/.default/
    ├── template.php     # только разметка, без запросов и логики
    ├── style.css        # стили шаблона — Bitrix подключит автоматически
    └── script.js        # скрипты шаблона — Bitrix подключит автоматически
```

Перед созданием нового компонента найди в проекте уже существующий
компонент с `Controllerable` и ассетами и повтори его структуру.
Если такого нет — эталон: разделение `executeComponent()` / `*Action()`,
ассеты в `templates/.default/`, тонкий шаблон.

## Компонент или include

- Блок страницы со своими данными, состоянием и JS — **отдельный компонент**,
  а не `require`/`include` куска разметки.
- `require __DIR__ . '/block.php'` внутри `template.php` запрещён, если блок
  содержит `style`/`script`/`link`, работает с DOM или делает свои AJAX-запросы.
- Мелкий фрагмент без поведения (иконка, одна строка) может остаться
  в шаблоне. Признак компонента: у фрагмента появляется свой JS,
  свои ассеты или своё состояние.

## Правила

### Класс
- Ровно один класс-наследник `CBitrixComponent` в `class.php`; Bitrix сам находит его при подключении компонента.
- Имя уникальное, глобальное (без namespace).
- Для AJAX-действий — `implements Controllerable`, методы `*Action`, `configureActions()` с `new Csrf()` на всём, что меняет данные.
- Данные пользователя брать из `CurrentUser::get()`, а не из параметров.

### Ассеты
- `style.css` и `script.js` шаблона лежат в папке шаблона:
  `templates/.default/style.css` и `templates/.default/script.js`.
  Bitrix подключает их автоматически при выводе шаблона — это штатная
  раскладка, переносить файлы в корень компонента не нужно.
- Если CSS/JS отдаются с **403**, это обычно не Битрикс и не кеш, а nginx:
  общее правило `location ~* /\. { deny all; }` закрывает сегмент `.default`.
  Нужно разрешить только статику в `templates/.default` **до** общего запрета:
  ```nginx
  location ~* ^/local/components/[^/]+/[^/]+/templates/\.default/.*\.(?:css|js|map|jpg|jpeg|gif|png|webp|avif|svg|woff|woff2|ttf|eot|ico)$ {
      expires 7d;
      access_log off;
      try_files $uri =404;
  }
  ```
  После правки — `nginx -t` и `nginx -s reload`.
- Не переносить ассеты в корень компонента как обходной путь: это ломает
  ожидаемое авто-подключение и расходится с раскладкой шаблона.
- `Asset` использовать, когда файл нужно подключить явно или вне шаблона:
  ```php
  Asset::getInstance()->addCss($this->getPath() . '/templates/.default/style.css');
  Asset::getInstance()->addJs($this->getPath() . '/templates/.default/script.js');
  ```
  Для обычного шаблона это не требуется: Bitrix подключит файлы сам.
- Теги `<link rel="stylesheet">` и `<script src>` в `template.php` запрещены:
  не дедуплицируются, ломают порядок загрузки и не кешируются Bitrix.
- Если ассеты не появляются, сначала проверить код ответа, а не кеш:
  `curl -I /local/components/.../templates/.default/style.css`.
  `403` — nginx, `404` — нет файла/пути, `200` — смотреть консоль и кеш.

### AJAX внутри компонента
- Класс реализует `Controllerable`; изменяющие действия объявляются
  в `configureActions()` с `new Csrf()`.
- Методы — `fooAction(...)` с типизированными параметрами, возвращают массив.
- Бизнес-логика остаётся в сервисах: экшен разбирает вход, проверяет права,
  вызывает сервис.
- Фронтенд вызывает действие через `BX.ajax.runComponentAction(...)` —
  CSRF-токен и подпись параметров подставляет ядро.
- Собственный `action.php` во внешней папке действий допустим только для
  вебхуков, cron и внешних вызовов. Для AJAX со страницы он не нужен
  и дублирует проверку CSRF.
- **Папки `templates/` в модуле быть не должно.** Модуль — это код (`lib/`, `config/`); разметка, стили и картинки живут там, где их рендерят.
- Общая разметка нескольких компонентов — отдельный маленький компонент (например `zavidovo:settings.nav`), а не копия в каждом шаблоне и не include из модуля.
- Картинки и иконки — всегда `local/templates/<template>/static/img/general/`: класть туда новый файл можно, править чужие иконки — нет. В модуль картинки не класть, даже если её открывает письмо, а не страница: письмо ссылается на публичный URL, а не на файл рядом с кодом.
- Стили, нужные двум и более компонентам (например деталка уведомления в колпачке и на странице), — в `static/css/backend.css` с комментарием-заголовком секции. Стили одного компонента — в его `templates/<template>/style.css`.

### Стили и скрипты
- `local/templates/*/static/css/main.css`, `static/js/main.js` и прочие файлы `static/` править **запрещено**.
- Свои стили — в `style.css` шаблона (`templates/<template>/style.css`).
- Стили компонента печатаются до `main.css`, поэтому при равной специфичности побеждает `main.css`. Если правило не применяется — повышать специфичность у себя, а не править `main.css`.
- Глобальные правки — только `backend.css` по согласованию.

### ORM D7
- Namespace полей: `Bitrix\Main\ORM\Fields\*`.
- `Bitrix\Main\Entity\*` использовать нельзя, кроме `DataManager`.
- ORM-описание должно совпадать с реальной схемой БД. Расхождение — дефект.
- Первичный ключ, уникальные индексы и nullable описываются явно.

### Миграции (Sprint Migration)
- Только добавочные файлы `VersionYYYYMMDDHHMMSS_*.php`; полный процесс и
  контентные миграции — скилл `migrations`.
- Существующие не редактировать.
- Повторный запуск безопасен: `CREATE TABLE IF NOT EXISTS`, проверки на существование колонки/индекса.
- Hazarды (backfill, изменение поведения) — с комментарием, объясняющим причину.

### Шаблоны
- `<?php`, не `<?`.
- Вывод только через `htmlspecialcharsbx` (или эквивалент).
- Состояния: пусто, загрузка, ошибка.
- Никакой бизнес-логики, только отображение.
- Шаблон не делает запросов к БД и внешним API, не считает деньги
  и не принимает решений: всё готовится в `executeComponent()` в `$arResult`.
- Пустые значения имеют явное состояние в разметке (`hidden`, заглушка, текст).
- Инлайн-стили — только для единичных значений; оформление в `templates/<template>/style.css`.
- Блок, нужный на нескольких страницах, выносится в компонент, а не копируется.

### Права и безопасность
- Админ-страницы: проверка прав в начале файла, до любого вывода.
- Списки подписок и секретов в админке не раскрывать.
- Ссылки из внешних источников пропускать через `SafeUrl`-подобную проверку.

## Проверка после создания компонента

1. `php -l` всех файлов; `node --check` для `script.js`.
2. Открыть страницу: CSS/JS отдаются с кодом 200 (не 403). При 403 сначала
   проверить nginx-правило для `templates/.default`, а не кеш Битрикса.
3. Проверить пустое состояние.
4. Проверить AJAX-действие с CSRF и без.
5. Проверить десктопную и мобильную ширину: блок не должен превращаться
   в узкую колонку на большом экране и ломаться на узком.
6. Убедиться, что блок подключён компонентом, а не `require` куска разметки.

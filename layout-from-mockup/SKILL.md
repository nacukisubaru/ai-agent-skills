# Вёрстка по макету и внедрение в проект

Скилл про **внедрение** готового макета. Извлечение данных из Figma — отдельный
скилл `figma-layout`; здесь начинается работа после того, как макет получен.

## Когда использовать

- Есть Figma-ссылка, готовый HTML/ZIP, скриншоты или PDF-макет.
- Задача говорит «сверстать», «переверстать», «редизайн», «применить верстку»,
  «сделать по макету».
- Нужно заменить интерфейс страницы, блока, компонента, хедера или футера.
- В проекте уже смешались старые и новые стили, и нужно навести порядок на
  конкретной поверхности.

Не использовать для бэкенда, API, миграций, правки контента и багфиксов без
интерфейсной части.

## 1. Источник макета

- **Figma** — сначала `figma-layout`: получить узлы, геометрию, шрифты, PNG.
- **Готовый HTML/ZIP** — сразу использовать как эталон, API Figma не нужен.
- **Скриншоты/PDF** — разобрать геометрию и стили, зафиксировать допущения.

Слепок хранить в папке задачи:

```text
.opencode/tasks/<slug>/mockup/
  index.html
  mobile.html
  mockup.css
  assets/
```

Для готового HTML — положить его в `mockup/` и не менять после согласования.
Слепок становится эталоном приёмки. Если макет неполный — зафиксировать пробелы
в `decisions.md`, а не додумывать молча.

## 2. Границы задачи

Макет не расширяет задачу. Границу задаёт карточка/ТЗ.

Определи уровень:

- **L1 — один блок или компонент.** Переделывается только он.
- **L2 — одна страница.** Переделывается страница целиком, включая её хедер и
  футер, если они есть в макете. Общие для сайта хедер/футер по умолчанию
  получают page-scoped вариант, а не меняются глобально.
- **L3 — весь сайт или несколько страниц.** Только если задача явно говорит
  «везде», «на всех страницах», «редизайн сайта». Тогда отдельный план на все
  страницы и общие компоненты.

Если из задачи непонятно, L1/L2/L3 это или нет — **не угадывать**. Задать вопрос
или выбрать самый узкий вариант, явно записать предположение в `plan.md` и
пометить его для подтверждения.

## 3. Контракт интерфейса в plan.md

Планировщик обязан зафиксировать:

- **Поверхность задачи:** страница / блок / компонент / хедер / футер.
- **Что переделываем:** список файлов, компонентов, шаблонов, селекторов.
- **Что не трогаем:** другие страницы, общие компоненты, глобальный CSS.
- **Разрешённые файлы:** что можно менять и создавать.
- **Запрещённые действия:** удалять глобальные стили, менять общие компоненты,
  трогать чужие страницы.
- **Переиспользование данных:** какие инфоблоки, API, ссылки, редиректы
  остаются. Интерфейс при этом всегда новый.

Внутри поверхности не должно остаться старой разметки, старых классов, старых
стилей и старых шаблонов. Снаружи — ничего не меняется.

## 4. Реализация

1. Создать новые компоненты/шаблоны под поверхность задачи.
2. Данные брать из существующих источников; ссылки и редиректы сохранить.
3. Старые шаблоны на целевой поверхности не подключать.
4. Не копировать готовый HTML в старый шаблон и не «подгонять» его старыми
   классами. Новый HTML — это новая разметка, а не заплатка.
5. Если блок общий для других страниц — сделать новый компонент/вариант для
   целевой страницы, старый оставить остальным. Глобально менять общий блок
   можно только в задаче уровня L3.
6. Глобальный старый CSS не удалять. Замена интерфейса = «на этой поверхности
   старые стили не используются», а не «удалить их из проекта».

## 5. CSS

- Стили компонента — в `templates/.default/style.css` компонента.
- Стили страницы/фичи — в отдельной папке по смыслу, путь задаётся правилами
  проекта. Для Bitrix обычно:

```text
local/templates/<template>/<feature>/
  tokens.css
  base.css
  header.css
  footer.css
  sections.css
```

- Не создавать один общий `style.css` на всю новую вёрстку: это повторяет
  проблему старого базового файла.
- Не писать новое в скомпилированный `static/dist/style.css` и аналогичные
  глобальные бандлы.
- Новый интерфейс изолировать префиксом классов (`zv-<feature>-...`) и scoped
  reset внутри корневого класса. Старый CSS может оставаться загруженным, но не
  должен влиять на новую поверхность.
- Шрифты, цвета и отступы — через CSS-переменные в `tokens.css`.
- Подключать page-level CSS явно и в порядке: `tokens → base → header → footer →
  sections`. Если файлов стало много — добавить сборку в один bundle, но
  исходники оставить смысловыми файлами.
- Не полагаться на `@layer` как на главный способ победить старый CSS: старые
  нелейерные стили могут быть выше по приоритету. Надёжнее префикс + reset.

## 6. Проверка

Обязательный parity-тест с `mockup/`:

- ширины 390 / 768 / 1366 / 1536;
- сравнение ключевых блоков по bounding box с допуском;
- сравнение computed styles: `font-family`, размер, вес, цвет, отступы;
- отсутствие горизонтального скролла и JS-ошибок;
- проверка, что на целевой поверхности нет старых классов/шаблонов;
- скриншоты для человека в `.opencode/playwright-mcp/`;
- `git diff --name-only` не выходит за разрешённый список файлов;
- другие страницы, использующие общие компоненты, не сломаны.

Если расхождение — исправлять реализацию, а не подгонять слепок. Менять
`mockup/` можно только по явному согласованию с человеком.

## 7. Definition of Done

- Поверхность задачи полностью соответствует макету.
- Внутри поверхности нет старых шаблонов, классов и стилей.
- Данные, ссылки и редиректы работают как раньше.
- CSS изолирован, глобальный старый CSS не задет.
- Другие страницы не изменились.
- Parity-отчёт и скриншоты приложены к задаче.
- Если что-то осталось за пределами поверхности — это явно записано в отчёте.

## 8. Типичные ошибки

- «Переиспользовать старый блок, потому что в нём уже есть вывод данных» —
  данные можно переиспользовать, интерфейс нельзя.
- «Вставить готовый HTML в старый шаблон и добавить новые стили сверху» — старые
  стили и разметка останутся внутри поверхности.
- «Оставить старый хедер/футер, потому что они общие» — если они в макете и в
  задаче, нужен новый page-scoped вариант.
- «Положить новые стили в общий `style.css`» — вернуть ту же свалку.
- «Проверить только скриншот» — старые шрифты и глобальные правила могут не
  бросаться в глаза; проверять computed styles и загруженные ассеты.
- «Расширить задачу на весь сайт, потому что макет большой» — границу задаёт
  задача, а не размер макета.

## 9. Связанные скиллы

- `figma-layout` — извлечение макета из Figma.
- `bitrix-component` — компоненты, шаблоны, ассеты Bitrix.
- `ui-testing-playwright` — браузерные проверки и скриншоты.
- `architecture` — новые классы, сервисы, репозитории.
- `migrations` — если для данных нужны новые поля/инфоблоки.

# Merge request

Ветка готова → пуш → MR в `dev` с описанием, которое **объясняет, что сделали**,
а не пересказывает дифф. Скилл исполняемый: доводит до ссылки на созданный MR.

## Когда применять

- Пользователь просит запушить ветку и открыть MR.
- Задача закончена, тесты и ревью зелёные, изменения должны уйти в `dev`.
- Нужно обновить описание уже открытого MR после новых коммитов.

## Жёсткие правила

- **Целевая ветка — всегда `dev`.** `master`/`stage` — только если пользователь
  назвал их явно.
- **Прямой пуш в `dev`, `stage`, `master` запрещён.** Пуш — только в ветку задачи.
- Источник изменений — ветка задачи, а не локальный `dev`.
- Секреты, пароли, токены, внутренние адреса и дампы **не попадают** ни в коммит,
  ни в описание MR.
- Описание MR — на русском (язык интерфейса и документации проекта).

## Шаг 1. Проверить ветку

```bash
git rev-parse --abbrev-ref HEAD
git status --porcelain                 # должно быть пусто
git fetch origin <target>
git log --oneline origin/<target>..HEAD
```

- Ветка = `dev`/`stage`/`master` → **стоп**, работать в ней MR не открывают:
  сказать пользователю и предложить ветку `feature/<slug>` или `fix/<slug>`.
- Рабочее дерево грязное → закоммитить (скилл `git-commits`) или спросить, что
  из изменений входит в MR.
- Коммитов впереди нет → MR создавать не из чего, сказать это.

## Шаг 2. Собрать саммари

Читать **в таком порядке**, ничего не додумывая:

1. `.github/tasks/<slug>/` — `review-*.md`, `plan.md`, `test-*.md`, `README.md`.
   Это основной источник: там уже сформулированы находки и что исправлено.
2. `git log origin/<target>..HEAD` — заголовки и тела коммитов.
3. `git diff --stat origin/<target>...HEAD` — какие области затронуты
   (компонент, модуль, миграции, шаблоны).
4. Контекст текущего чата — что просил пользователь и что осталось непроверенным.

Если папки задачи нет — опираться на коммиты и дифф, но **не выдумывать**
причины изменений: писать только то, что видно в коде и коммитах.

## Шаг 3. Описание MR

Шаблон (пустые разделы лучше убрать, чем оставить заглушки):

```markdown
## Что сделано

- <группа изменений>: <результат для пользователя>
- ...

## Как проверено

- `php -l` / `node --check` — ...
- Ручной сценарий: `.github/tests/<slug>/` — N OK, 0 FAIL
- `make aggregator-test-unit` — N тестов, OK

## Затронуто

<компоненты, модули, миграции, шаблоны — кратко>

## Осталось / риски

- <что не входит в MR, что требует отдельного решения>
```

Правила текста:

- Формулировки — про поведение («сортировка открывает меню и меняет `?sort=`»),
  а не про файлы («изменён template.php»).
- Одна строка — одна законченная мысль, без «разное», «мелкие правки».
- Найденные по ходу баги и их причина — отдельным пунктом: это самое ценное
  в описании.
- Если менялись миграции — указать, что накатывается автоматически и что
  повторный запуск безопасен.
- Объём: 5–15 пунктов. Длиннее — значит, MR стоит разбить.

## Шаг 4. Пуш и создание MR

Создание MR из push options токен не требует — работают те же права, что и на
обычный пуш. **Но push options не принимают переводы строк** (`git` отвечает
`push options must not have new line characters`), поэтому описание в них не
передать: push options создают MR с заголовком, описание ставится через API
(шаг 5).

```bash
git push -u origin HEAD \
  -o merge_request.create \
  -o merge_request.target=<target> \
  -o merge_request.title="<заголовок>" \
  -o merge_request.remove_source_branch
```

- `<target>` — по умолчанию `dev`.
- Заголовок — английский, императив, как у коммита, до ~72 символов.
  Например: `Fix catalog sort, landing links and filter slider bounds`.
- Значение любой опции — **одна строка**. Кавычку внутри экранировать (`\"`),
  иначе git обрежет опцию.
- Если целевая ветка уже содержит эти коммиты (fast-forward), GitLab может
  отклонить создание — тогда MR не нужен, сказать это пользователю.

GitLab печатает в ответ ссылку вида
`remote: View merge request for <branch>: https://.../merge_requests/<n>` —
**это и есть результат**, ссылку отдать пользователю.

Если MR для ветки уже открыт, повторный пуш с `merge_request.create` новый
не создаёт: MR обновляется коммитами. Описание при этом не меняется — тогда
дописать его через API (шаг 5).

## Шаг 5. Описание MR через API

Обязательный шаг: push options описание не передают. Нужен токен
`GITLAB_TOKEN` из `.github/.env.local` (имена переменных — в
`.github/project-features.md`).

- Токен в команды и логи не печатать, из `.env.local` читать в переменную
  окружения.
- Нет токена → **спросить пользователя одним вопросом** и не выдумывать
  обходные пути; MR при этом уже создан с заголовком, сказать об этом.
- Ответ пользователя дописать в `.env.local`, а не в скилл.

```bash
PROJECT=$(python3 -c 'import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1], safe=""))' "<group/project>")
# iid — из ссылки, которую напечатал push (последний сегмент URL)
curl -s --request PUT \
  --header "PRIVATE-TOKEN: $GITLAB_TOKEN" \
  --data-urlencode "description@mr-description.md" \
  "https://<host>/api/v4/projects/$PROJECT/merge_requests/<iid>"
```

- `--data-urlencode "description@file"` читает описание из файла: переводы строк
  и кавычки не ломаются.
- Успех — JSON с `"iid"` и заполненным `description`; ошибка — `message`.
- Если токена нет совсем и пользователь не может его дать — создать MR с
  заголовком и **честно сказать**, что описание не заполнено.

## Шаг 6. Отчитаться

Пользователю — коротко:

- ссылка на MR;
- целевая ветка;
- число коммитов;
- что осталось (если есть);
- если MR создать не удалось — текст ошибки git/GitLab и что именно сделать
  руками, без догадок.

## Запрещено

- Пушить в `dev`/`stage`/`master` вместо ветки задачи.
- Создавать MR без описания или с описанием из заголовков коммитов.
- Указывать в описании пароли, токены, доступы, внутренние хосты.
- Переписывать историю ветки после пуша без явной просьбы (это делает
  скилл `git-commits`, и только по подтверждению).
- Открывать MR из ветки, где не проходили тесты и ревью, если пользователь
  не сказал, что проверит сам.

# codebase-memory: сначала граф, потом grep

## Главное правило

**Любой поиск по коду начинается с codebase-memory.** grep — фолбэк, а не первый выбор.

Действует на:

- меня;
- любого субагента, которому я даю задачу на поиск.

Ключевой нюанс: правило применяется **к каждому новому вопросу**, а не один раз за задачу.
Если grep уже пригодился, это не значит, что дальше надо искать только грепом. Следующий
вопрос — снова начинается с графа.

```
новый вопрос о коде
        │
        ├─ codebase-memory отдал результат ──────► использовать, grep не нужен
        │
        ├─ пусто / не то / путь вне индекса ─────► grep
        │                                            │
        │                                            └─ получилось ─► работаем
        │
        └─ следующий вопрос ─────────────────────► снова с codebase-memory
```

Запрещено:

- Начинать с `grep`/`rg`/`glob`, потому что «так быстрее».
- Оставаться в режиме grep до конца задачи после первого фолбэка.
- Считать, что «в графе нет» = «в проекте нет». Это разные утверждения: см. покрытие ниже.

## Что чем искать

| Задача | Инструмент |
|---|---|
| Найти класс, метод, сервис, маршрут по смыслу | `search_graph` с `query` |
| Найти по точному шаблону имени | `search_graph` с `name_pattern` (regex) |
| Найти по смыслу, когда слова не совпадают («отправка» → `publish`) | `search_graph` с `semantic_query` (массив слов) |
| Кто вызывает / что вызывает | `trace_path` (`direction` = `inbound` / `outbound`) |
| Прочитать тело функции | `get_code_snippet` по `qualified_name` |
| Архитектура, слои, кластеры | `get_architecture` |
| Структурные вопросы (счётчики, сложность, fan-in) | `query_graph` |
| Строки внутри проиндексированных файлов | `search_code` |
| Что изменилось и что заденет | `detect_changes` |

Порядок для незнакомого места: `search_graph` → `trace_path` → `get_code_snippet`.
Читать файл целиком, чтобы найти один метод, нельзя.

### Полезные свойства узлов

У `Function`/`Method` есть готовые метрики: `complexity`, `cognitive`, `loop_depth`,
`transitive_loop_depth`, `linear_scan_in_loop`, `recursion_in_loop`, `param_count`.
Ими хорошо отвечать на «где тут узкое место», не читая код:

```
MATCH (f:Function) WHERE f.transitive_loop_depth >= 3
RETURN f.qualified_name, f.transitive_loop_depth ORDER BY 2 DESC LIMIT 20
```

## Покрытие индекса в этом репозитории

Проверено на индексе `aggregator` (корень `/Users/aleksandrkrestinskij/projects/aggregator`):

| Путь | В индексе |
|---|---|
| `project/src/**` | да (~90 файлов) |
| `project/tests/**` | да (~164) |
| `project/config/**` | да (~22) |
| `project/services/**` | да |
| **`project/public/**`** | **нет** |

Отсюда практический вывод: **компоненты, модули, шаблоны и админки Bitrix
(`project/public/local/...`) граф не содержит.** Для них «codebase ничего не нашёл»
ожидаемо, и grep — законный следующий шаг, а не нарушение правила.

Исключения из индексации заданы в `.cbmignore` (Bitrix core, vendor, upload, `.github`).

Если вопрос про `project/public/**` — сразу сказать это и перейти к grep, не тратя
три попытки на граф.

## grep: когда законен

- Цель под `project/public/**` (компоненты, модули, шаблоны, админки).
- Список файлов по маске.
- Проверка, что строка реально появилась/исчезла после правки (перед `edit`/после).
- Конфиги, `.env`, миграции, текстовые файлы, документация — если их нет в графе.
- Подтверждение результата собственной правки.

Не законен как способ «понять, как устроен проект».

## Субагенты

Read-only субагенты (`code-review`, `explore`) **не имеют доступа** к codebase-memory.
Поэтому правило передаётся словами в промпте, иначе субагент по умолчанию пойдёт в grep.

Что писать в промпт при запуске:

```
Поиск: сначала codebase-memory (проект `aggregator`), только если пусто — grep.
Покрытие: project/src, project/tests, project/config, project/services — есть;
project/public/** (компоненты/модули Bitrix) — нет, там сразу grep.
Не начинай с grep и не оставайся в нём после первого фолбэка.
Верни: файл, диапазон строк, что именно нашёл.
```

Дополнительно:

- Один субагент — один узкий вопрос с критерием остановки.
- Если цель заведомо в `project/public/**` — сразу передавать файлы и диапазоны строк,
  поиск в нём бессмысленен.
- Нет ответа ~5 минут или больше 40 вызовов — остановить и сделать самому.

## Индексация

- Запускать **только** при пуше, и только с подтверждения пользователя.
- Не индексировать после правок, «на всякий случай», в начале задачи.
- Устаревшие узлы — не повод индексировать.
- После правки кода индекс не обновляется: `get_code_snippet` может показать старую
  версию. Свежий код читать из файла, а не из графа.

## Если инструмент недоступен

Бывает, что MCP-сервер не поднялся или проект не проиндексирован. Тогда:

1. Сказать об этом пользователю одной строкой.
2. Перейти к grep по правилам выше.

Молча заменять граф грепом нельзя: пользователь должен понимать, почему поиск другой.

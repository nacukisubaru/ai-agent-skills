# Вход в Bitrix

## Когда применять

- Нужна сессия администратора Bitrix: проверка интерфейса, съёмка скриншотов
  для PDF-инструкции, ручной сценарий в админке.
- Форма входа не пускает: капча, код, «слишком много попыток».

Для других платформ (не Bitrix) этот скилл не подходит — у них свой способ входа.

## Где брать доступы

Скилл общий для всех проектов, поэтому доступов в нём нет. Порядок всегда один:

1. **`.github/project-features.md`** — особенности проекта: адрес стенда,
   **имена** переменных с доступами, ожидаемый id пользователя. Файл локальный,
   в git не попадает.
2. **`.github/.env.local`** — значения этих переменных. Тоже локальный.
3. **Нет нужной переменной — спросить у пользователя.** Не подбирать пароль,
   не пробовать чужие учётки, не заводить нового пользователя. Ответ дописать
   в `.env.local`, а не в файл скилла.

Стандартные переменные: `SITE_BASE_URL`, `SITE_ADMIN_LOGIN`, `SITE_ADMIN_EMAIL`,
`SITE_ADMIN_PASSWORD`.

## Как входить: мост вместо формы

Форма входа Bitrix закрывается капчей после нескольких неудачных попыток, поэтому
вход делается одноразовым PHP-скриптом, который вызывает `$USER->Login()`
и удаляется сразу после проверки.

1. Создать файл в публичной части проекта, путь из `project-features.md`
   (обычно `project/public/local/tmp-login.php`):

```php
<?php
require $_SERVER['DOCUMENT_ROOT'] . '/bitrix/modules/main/include/prolog_before.php';
global $USER;
header('Content-Type: text/plain; charset=utf-8');

// Bitrix Login() принимает LOGIN, а не email: при входе по почте находим LOGIN.
function shot_resolve_login(string $value): string
{
    if (strpos($value, '@') === false) {
        return $value;
    }
    $row = CUser::GetList('id', 'asc', ['EMAIL' => $value], ['FIELDS' => ['ID', 'LOGIN']])->Fetch();
    return $row ? (string)$row['LOGIN'] : $value;
}

$login = '<SITE_ADMIN_LOGIN или SITE_ADMIN_EMAIL из .env.local>';
$pass  = '<SITE_ADMIN_PASSWORD из .env.local>';
$ok = $USER->Login(shot_resolve_login($login), $pass, 'Y');
echo $ok ? 'OK user=' . (int)$USER->GetID() : 'FAIL: ' . $USER->LAST_ERROR;
```

2. Открыть его в браузере (или через `curl`) — должно быть `OK user=<id>`.
   Ожидаемый id записан в `project-features.md`; другой id — это чужой пользователь,
   проверять права.
3. Перейти на нужную страницу — сессия уже есть.
4. **Удалить файл.** Он не должен оставаться ни в рабочей копии, ни в git.

`scripts/shot.mjs` в скилле `pdf-instructions` делает всё это сам: создаёт мост,
входит, снимает и удаляет файл. Ручной мост нужен только для `playwright-mcp`
и разовых проверок.

## Особенности Bitrix, из-за которых вход не работает

- **LOGIN ≠ EMAIL.** `$USER->Login()` принимает только `LOGIN`. В базе он часто
  технический (`prefix_<hash>_<email>`), даже если человек помнит свою почту. Поэтому
  мост сначала ищет пользователя по `EMAIL` и подставляет найденный `LOGIN`.
- **`USER->LAST_ERROR`** печатать безопасно, пароль туда не попадает; но текст ошибки
  не должен уходить в отчёт вместе с логином.
- **Капча и коды** на форме входа: повторные неудачные попытки блокируют вход,
  поэтому форма не используется вообще.
- **Сессия без API-куки.** Мост даёт Bitrix-сессию, но не ставит HttpOnly-куку
  авторизации приложения (в этом проекте — отдельная кука приложения). Приватный API ответит
  «Требуется авторизация»; для таких сценариев нужен штатный вход через приложение.

## Запрещено

- Оставлять мост или любой другой файл с логином и паролем в проекте и в git.
- Хардкодить доступы в скилле, скрипте, шаблоне, `tasks.json` и отчёте.
- Печатать пароль в лог, консоль, скриншот или текст инструкции.
- Подбирать доступы и заводить пользователя вместо запроса у пользователя.

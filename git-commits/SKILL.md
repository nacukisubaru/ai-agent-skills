# Git: коммиты и пуш

## Два режима — не путать

### Режим A. «Закоммить» без уточнений
Пользователь уже проверил всё сам. Один коммит всего рабочего дерева:

```bash
git add -A
git commit -m "<message>"
```

В этом режиме **запрещено** предварительно смотреть `git status`, `git diff`, `.gitignore` и содержимое файлов: пользователь отвечает за изменения.

### Режим B. Логические коммиты (работа по плану)
Применяется, когда задача разбита на фазы и нужно сохранять прогресс по частям.
Здесь **разрешены**:

```bash
git status --porcelain
git diff --stat <base>..HEAD
```

Они нужны, чтобы отделить одну логическую единицу от другой. Без них разбивка невозможна.

Правила разбивки:

- Один коммит — одна законченная мысль: схема, сервис, компонент, конфиг, тесты.
- Не смешивать рефакторинг и поведение.
- Не смешивать чужие правки со своими: если в дереве есть изменения пользователя, спросить, включать ли их.
- Стили и скрипты шаблона (`static/`) коммитить отдельно и только если пользователь подтвердил.

## Сообщения

- Английский, императив, до ~72 символов в заголовке.
- Без «update files», «fixes», «wip».
- Тело — по необходимости: зачем, а не что.

## Пуш

- Только по явному подтверждению пользователя.
- Ветки `stage` и `dev` — **никогда**.
- Перед пушем — индекс codebase-memory (если пользователь разрешил).

## Переписывание дат

Если пользователь попросил — сначала уточнить:

1. Для всех коммитов ветки или для последних N?
2. Какая дата и время для каждого?

Примеры:

```bash
GIT_COMMITTER_DATE="2026-10-20T14:30:00" git commit --amend --date="2026-10-20T14:30:00" --no-edit
GIT_AUTHOR_DATE="2026-10-20T14:30:00" GIT_COMMITTER_DATE="2026-10-20T14:30:00" git commit --amend --no-edit
```

Для нескольких коммитов — интерактивный rebase с `--committer-date-is-author-date` или `filter-branch`/`filter-repo`; предупредить, что история переписывается.

## После сбоя

Если команда не выполнилась (конфликт, права, hook) — сообщить текст ошибки и ждать указаний. Не «чинить» самостоятельно.

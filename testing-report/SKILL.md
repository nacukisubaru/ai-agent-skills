# Отчёт о тестировании

## Когда применять

- В конце **каждой фазы** — отчёт по этой фазе.
- После завершения **всей задачи** — один финальный отчёт по всем фазам.
- Когда пользователь просит «напиши, как тестировать», «сценарий для тестировщика»,
  «QA-отчёт», «инструкцию по проверке».

Это не замена `test-N.md` (результаты реальных прогонов) и не замена `code-review`.
Здесь — инструкция для человека, который будет проверять задачу.

## Где лежит

```
.opencode/tasks/<slug>/
├── testing-report-phase-1.md
├── testing-report-phase-2.md
└── testing-report-final.md
```

- `test-N.md` — что реально прогнали и что получилось.
- `testing-report-*.md` — что и как проверять, с данными и ожидаемым результатом.

PDF — **только если пользователь явно попросил**. Если попросил, делаем PDF в конце
каждой фазы и один финальный, по правилам скилла `pdf-instructions`:

```
.opencode/docs/instructions/<slug>-phase-N/
.opencode/docs/instructions/<slug>-final/
```

В отчёте — ссылка на PDF. Если PDF не просили, никаких HTML, PDF и скриншотов
не создаём: только Markdown.

## Структура отчёта

### 1. Шапка

- задача и фаза (`Фаза 2 из 5` или `Финальная проверка`);
- дата, ветка, коммит;
- стенд и окружение;
- что именно изменилось в этой фазе (1–3 строки);
- ссылки на `plan.md`, `review-N.md`, `test-N.md`.

### 2. Данные для тестирования — в самом начале

Тестировщик должен получить всё до первого шага:

- адрес сайта, админки, API;
- пользователь, роль, ожидаемый id;
- **имена** переменных с доступами и где значения:
  `.opencode/project-config.md`, `.opencode/.env.local`, `secrets/*.json`;
- тестовые сущности: ID, CODE, XML_ID, названия, email;
- сиды/фикстуры и команды подготовки:
  миграции, наполнение БД, очистка кеша, фича-флаги;
- что уже должно быть применено (миграции, настройки, контент);
- команды очистки/откат после проверки;
- что нельзя трогать (продовые данные, чужие учётки, реальные письма).

Пароли и токены в отчёт не вставляем — только имена переменных.

### 3. Общий сценарий проверки

Минимальный путь, который доказывает, что задача работает:

1. Подготовка: что открыть, что включить, какие данные создать.
2. Шаги по порядку: действие → ожидаемый результат.
3. Как проверить результат: UI, API, БД, логи, письмо, счётчик.
4. Что считается успехом и что — ошибкой.
5. Очистка.

Шаги должны быть конкретными: точные пути, названия кнопок, поля, селекторы,
команды. Не «нажмите нужную кнопку».

### 4. Сложные и критические кейсы

Добавляем то, что легко пропустить и что реально ломает задачу:

- права и роли: чужой пользователь, гость, администратор;
- пустые данные, одна запись, много записей, лимиты;
- повторный запуск, дубли, идемпотентность;
- конкурентные действия и блокировки;
- недоступность внешнего сервиса, таймаут, ошибка API;
- миграции: повторный запуск, откат, данные до/после;
- регрессия соседних сценариев;
- изоляция данных между пользователями/сайтами;
- откат и восстановление после сбоя.

Для каждого кейса: зачем он нужен, подготовка, шаги, ожидаемый результат.
Приоритет — critical/high; не раздувать отчёт косметикой.

### 5. Финальный отчёт

После всех фаз:

- сквозной сценарий по всей задаче, а не только по последней фазе;
- ссылки на отчёты фаз и реальные `test-N.md`;
- полная регрессия затронутых областей;
- что осталось непроверенным и почему;
- известные риски и ограничения.

### 6. Чек-лист

- [ ] общий сценарий пройден;
- [ ] критические кейсы проверены;
- [ ] данные и окружение описаны;
- [ ] очистка выполнена;
- [ ] отчёт дополнен фактическим результатом;
- [ ] PDF собран — только если просили.

## Правила

- Отчёт самодостаточен: тестировщик не должен читать чат или код, чтобы понять шаги.
- Команды и пути — реальные, из `.opencode/project-rules.md` и
  `.opencode/project-config.md`; не выдумывать.
- Перед сдачей пройти общий сценарий самому; если это невозможно — явно написать,
  что и почему не проверено.
- Обновить `progress.md` фазы и статус в `plan.md`.
- Отчёт фазы создаётся до коммита фазы; финальный — после последней фазы.
- PDF только по явной просьбе. Если попросили — PDF на каждую фазу и финальный,
  со скриншотами по шагам (скринкаст-формат); без паролей, реальных почт и
  персональных данных.

## Запрещено

- Отчёт без данных для тестирования и команд подготовки.
- Только happy path без критических кейсов.
- «Проверьте, что всё работает» вместо шагов и ожидаемого результата.
- Секреты, пароли и персональные данные в тексте, скриншотах и PDF.
- Создавать PDF, когда пользователь не просил.
- Подменять `test-N.md` отчётом о тестировании: это разные документы.
